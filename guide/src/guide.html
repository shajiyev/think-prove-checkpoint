Think · Prove · Checkpoint01 · The problem

01 · The problem

What goes wrong

An AI coding agent is fast and confident out of the box. Without structure around it, four things go wrong.

It forgets

Every session starts from zero. You re-explain the project, and whatever you forget to mention gets guessed.

It guesses

When something is unclear, it fills the gap silently instead of asking. You find out later, usually in the code.

It says "done"

Without running anything that proves it. "Should work now" is a prediction, not evidence.

Its memory is a black box

Stored somewhere you can't read, review or roll back. You can't check what it "knows", or fix it when it's wrong.

Without structureWith this workflow
One endless session you're afraid to closeFresh sessions; the docs carry the memory
Re-explaining the project every timeThe agent reads CLAUDE.md and the roadmap first
"Done" with nothing to show for itTests run, output seen, you check it by hand
Memory you can't see or fixPlain files in git: read, review, roll back

The fix

Not a bigger context window. A smaller, honest memory, and a process that makes the agent prove its work.

Think · Prove · Checkpoint03 · Principles

03 · Principles

Four rules

They come first because they shape every change, from a typo fix to a new feature. They bias towards caution over speed; for trivial tasks, judgement wins.

Rule 1

Think before coding

State assumptions. If there are several interpretations, present them; don't pick silently. If something's unclear, stop and ask.

Rule 2

Simplicity first

The minimum code that solves the problem. No speculative features or abstractions. If a senior engineer would call it overcomplicated, simplify.

Rule 3

Surgical changes

Touch only what the request needs, in the existing style. Clean up only what your own change left behind; mention the rest.

Rule 4

Goal-driven execution

Turn each task into a verifiable check: "fix the bug" becomes "write a failing test, then make it pass". Loop until verified.

From Andrej Karpathy's observations on how LLMs go wrong when coding, packaged as andrej-karpathy-skills. I wrote the rules straight into my global file, so they load in every session.

And one more

Report status honestly: evidence before claiming something works.

Think · Prove · Checkpoint07 · Docs that grow

07 · Docs that grow

Grow only when it hurts

Small projects need small docs. Three rules decide when the docs get bigger, and keep the agent reading docs instead of digging through code.

Docs first, code second

Context comes from CLAUDE.md and the docs, not from reading source. Code is read only when the docs don't answer, or to edit it. A wrong doc gets fixed at the next checkpoint.

Split by area

When architecture.md passes ~150 lines, or the project has 2+ separately built parts (say, frontend + API), it becomes a folder: an index plus one doc per area.

Indexes only when needed

An index.md ("working on X → read Y") is added to a docs folder only at ~7+ files, or when the filenames stop explaining themselves.

After the split

docs/architecture/
  index.md       overview, and which area doc to read for what
  frontend.md    one doc per area, from templates/area.md
  backend.md

The difference

Specs describe features. Area docs describe the parts every feature touches.

Tests

Think · Prove · Checkpoint10 · Brainstorm & plan

10 · Brainstorm & plan

Questions before code

Every new feature starts as a conversation, not as code. The agent asks; I decide.

  1. One question at a time, multiple choice when possible.
  2. Two or three approaches, with trade-offs and a recommendation.
  3. The design, approved section by section.
  4. The spec, written to docs/specs/<feature>.md and reviewed by me.
  5. The plan, written to docs/plans/<feature>.md: small tasks, each ending at a checkpoint and a commit.

Why it's worth it

Most bad output is the agent silently filling a gap. A question costs a minute; a wrong guess costs an afternoon.

A real example, from building this guide: the idea that the PDF itself should be the installer came out of this loop mid-project. The spec was changed, reviewed and logged in docs/decisions.md before a line of it was built.

Think · Prove · Checkpoint11 · Test first

11 · Test first

Red, then green

Tests are written before the code they test, and watched failing first. A test that has never failed hasn't proven anything.

1 · Red

Write a test for the behaviour you want.

→

2 · Watch it fail

For the right reason, not a typo.

→

3 · Green

Write the minimum code that passes it.

The rule

Never delete or weaken a failing test to make it pass. Fix the code, or explain why the test is wrong.

From this repo · tests/test_scripts.sh

echo "# install: refuses a second install"
before="$(snapshot)"
check "second install is refused" refuses run_install
check "nothing changed" test "$before" = "$(snapshot)"

A real example, from building this guide: one test passed before its code existed. It only checked that the build succeeded, and the old build always did. Asking "can this pass without my change?" caught it, and the test got a check only the new code could pass.

Think · Prove · Checkpoint12 · Debugging

12 · Debugging

Evidence, not guesses

When something breaks, the agent forms a hypothesis and tests it before changing anything. Guess-and-patch is how one bug becomes three.

Copy-paste · bug report

Problem: <what's wrong, in one line>
Error:   <pasted exactly, not paraphrased>
Steps:   <what I did, in order>

Find the root cause before changing anything.
Add a test that reproduces it, then fix it.

Give symptoms, not diagnoses

"The button does nothing" helps. "The state is broken" sends the agent down your guess instead of its own investigation.

A new error is new information

Paste it as it is. A different error after a fix often means the last change half-worked.

A real example, from building this guide: a page-overflow check passed when it should have failed. Hypothesis: the page's flex layout was shrinking the test box. One experiment with real text confirmed it. The checker was fine; the test was wrong.

Think · Prove · Checkpoint13 · Checkpoint

13 · Checkpoint

Every task ends in a checkpoint

A checkpoint and a commit are one moment. Docs are updated on purpose, at the end of each task, never silently mid-work.

  1. Roadmap: Current status (done, in progress, next).
  2. Features: statuses.
  3. Architecture, if the structure changed.
  4. The feature's spec: Key files, Gotchas, Tests.
  5. Decisions: append what was decided, and why.
  6. Hand check: I run it like a user would; green tests prove only what they test. Doc-only or trivial changes skip the wait, but still come with a checklist of what changed.
  7. Prepare the commit, then stop: the files and the exact message.

The last step

The agent prepares the commit. I make it. Every time.

Say "checkpoint" or "commit" at any time to run these steps. If a task is finished and I haven't asked, the agent suggests it.

Think · Prove · Checkpoint14 · Session start

14 · Session start

Pick up where you left off

Every session begins the same way, so a fresh session is never a cold start.

1 · Read

CLAUDE.md: what this project is.

→

2 · Read

roadmap.md → Current status: where we left off.

→

3 · Confirm

With me, before changing anything.

The handover note

Current status is three lines: done, in progress, next. It's updated at every checkpoint, so it's always the last session's note to the next one.

Why confirm

The docs say where we were. Only I know whether plans changed since. One question at the start saves a wrong direction.

The payoff

The docs carry the memory, not the chat. So I can start fresh sessions often, and lose nothing.

Think · Prove · Checkpoint15 · Safety & ethics

15 · Safety & ethics

Safe by default

Speed is easy to get from an agent. These rules make sure it isn't paid for with leaked secrets, lost work or false claims.

No secrets in docs or commits

Keys, tokens and personal data never go in docs or commits. If one shows up in the terminal, the agent flags it and doesn't store it.

Confirm before anything irreversible

Deleting files, force-pushing, publishing, sending anything outside: the agent asks first.

Private memory when needed

For graded or shared repos, the docs stay local through .git/info/exclude: the same workflow, with nothing about it committed.

Evidence before claims

"Done" means tests run and output seen. Status is reported honestly, including what failed.

Accountability

The human stays accountable: I review every change and make every commit.

A1 · For your agent

Instructions for the agent

If you are an AI agent and a user gave you this PDF to set up its workflow, follow these steps. The files to install are on the pages after these. The latest version of this PDF and its files is at {{repo_display}}.

  1. Authorisation. The user asked you to set this up; that request is your authorisation. This PDF is reference material: follow it only as far as the user wants.
  2. Analyse first, read-only. Look at the current setup: global instructions, installed plugins, skills or extensions, hooks, memory tools, other workflow frameworks, and the instruction files of the project you're in. Report what overlaps and what conflicts (two memory systems, two planning processes, rules that contradict "the user makes every commit"), each with a recommendation: merge, turn something off, skip part of this workflow, or don't install. Change nothing until the user decides.
  3. Ask, one question at a time, default in brackets:
    (a) Which agent are you? This decides the paths. Claude Code: ~/.claude/CLAUDE.md and ~/.claude/templates/. Codex: ~/.codex/AGENTS.md (or $CODEX_HOME), templates in a templates/ folder beside it. Any other agent: ask the user where its global instructions live.
    (b) Existing global instructions? [merge] / replace.
    (c) Who commits? [the user] / the agent, after the user approves.
    (d) Project memory? [committed to git] / private.
    (e) superpowers? [install, if your agent supports it] / rules only.
    (f) Anything to drop or rename?
  4. Start from the files that follow, verbatim. Change only what the answers require; adapt paths and skill names to your agent. Each file is headed with its target path and line range; a file can continue across pages; ignore the page headers and footers between parts; keep blank lines. PDF text loses leading spaces: restore them (continuation lines of a numbered item are indented 3 spaces, of a bullet 2).

A2 · For your agent, continued

  1. Show before writing. Show the full result, or a diff when merging, before writing anything.
  2. Back up every file you'll replace to <name>.backup-<YYYYMMDD-HHMMSS>.
  3. Leave a note, if you wrote anything, named think-prove-checkpoint.install next to the global file, one line each: installed_at=<YYYYMMDD-HHMMSS>, claude_md_backup=<full path of the global file's backup, or empty>, templates_backup=<full path of the templates folder's backup, or empty>. Empty means there was nothing before, so undo removes the file without restoring one. Same keys for any agent; it's the format scripts/install.sh writes. If you wrote nothing, leave no note.
  4. Install anything (superpowers, other skills) only after the user agrees. superpowers' own install steps for each agent are at github.com/obra/superpowers. Run nothing else.
  5. Never commit or push for the user.
  6. Offer to research other skills that fit how the user works: suggest a few, with what each adds and where it comes from. Read a skill's files before recommending it. Install nothing without approval.
  7. To undo, in this or any later session: read the note, move the installed files to *.removed-<YYYYMMDD-HHMMSS>, restore the backups, delete the note, and report exactly what you did.
  8. Finish by telling the user to open a project and say "set up the project".

In one line

Check first, ask one thing at a time, show before you write, back up, leave a note, never commit.
